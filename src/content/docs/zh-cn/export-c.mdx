`c2go_extern` 会通过生成的 package 导出一个**已经定义的** C 函数。Managed record 元数据则让 `c2go-bind` 暴露与之匹配的 Go 可见布局。

## 导出函数

```c
#include <c2go.h>
#include <stddef.h>
#include <stdint.h>

c2go_extern int64_t sum(const int64_t *values, size_t count) {
    int64_t total = 0;
    for (size_t i = 0; i < count; ++i) {
        total += values[i];
    }
    return total;
}
```

公开 API 建议使用固定宽度整数。`long` 在 Linux/macOS 64 位 target 上是 64 位，在 Windows 64 位 target 上仍是 32 位；除非这个差异就是契约的一部分，否则不要用它表达跨平台 Go API。

默认 Go 导出名会把每个下划线分段转换为 CamelCase，并移除下划线：`sum` 变为 `Sum`，`is_upper` 变为 `IsUpper`，`sqlite3_open` 变为 `Sqlite3Open`。package path 由 `-fc2go-package` 和 `c2go-bind --pkg` 共同指定。

只有现有契约确实要求保持拼写时，才使用 `c2go_extern_as(C2GO_KEEPCASE)`：

```c
c2go_extern_as(C2GO_KEEPCASE)
int ParseID(const char *text) { /* ... */ }
```

声明与定义必须一致。应在第一次声明上写 `c2go_extern`；只在后续 redeclaration 中补上会被拒绝。

## 导出 managed record

```c
struct managed Point {
    double x;
    double y;
};

c2go_extern struct Point translate(
    struct Point point,
    double dx,
    double dy
) {
    point.x += dx;
    point.y += dy;
    return point;
}
```

manifest 会记录 size、字段 offset 和 pointer layout。`c2go-bind` 根据这些事实生成 Go 兼容类型，而不是从宿主编译器默认值猜测。

Managed record 不能 packed，也不能覆盖单个字段的 alignment，因为 Go 契约中没有对应布局。

## Go 保留名称

导出的 `init` 或 `main` 函数不能保留小写名。这些名称在 Go 中具有语言级语义，因此 C2Go 会拒绝可能产生冲突的导出。

## 保持生成 package 完整

除了表面可见的声明，生成文件还包括 ABI/版本 guard，并可能包含 runtime import、GC metadata 或 native-call glue。不要只复制看起来像公共 API 的 `.go` 文件；应完整保留整个生成目录及其授权记录。

反向操作——声明并调用已有 Go 符号——见[从 C 调用 Go](/zh-cn/docs/call-go/)。
